# ラウンド設計標準と第1回ラウンド仕様（ドラフト）

作成: 2026-08-26 / ブランチ: `design/fable-testnet` / 状態: **ドラフト（数値・日程は人間承認前）**

前提: `docs/fable-concept.md` 追記10。TradeCoreは「異質な仮説の書庫（順位なし）」と「同質なラウンドの競技場（順位あり・信頼区間つき）」の二層を持つ。この文書は後者の設計標準と、第1回の具体案。

設計手順は北山朝也「botterのためのKaggle金融予測コンペの設計史」のチェックリスト7項目に従う。観測スコアの分解 Q̂ = Q + δ_regime + ε_sampling + b_feedback + b_protocol の各項を、どの設計で抑えるかを明示する。

## 第1回ラウンド仕様

### 1. Q（識別したい質）

**Hyperliquid perpユニバースの1〜4日先の相対リターンの順序を、日々安定して当てる力（LS＝マーケットニュートラルなロング・ショートのsignalに限定）。**

- 第1回はLSに絞る（ユーザー決定 2026-08-26）。方向性ベット（絶対リターン予測）はラウンドの採点対象外で、仮説の書庫レーンで扱う。相対順序のみを採点することで、採点対象がそのままドルニュートラルL/Sの構築材料になる。
- alphaの質を測る（ポートフォリオ効用は測らない。bet sizingやリスク管理は昇格審査側の仕事で、ラウンドはsignal発見に特化する。Hull型のpolicy評価ラウンドは将来の別形式）。
- 執行層がHLである以上（追記9）、ここで見つかるsignalは実資金採用まで同じ土俵で持ち込める。
- 設計参照（MITSUI型の5要素をすべて第1回に採用）: Rank評価（Spearman、価格・ボラスケールと外れ値を抑える）／Daily IC（特定日・特定銘柄の支配を抑える）／IC Sharpe（日付方向の不安定性を抑える）／Multi-horizon 1〜4日混在（単一horizonだけに効く偶然を希釈）／約90日の提出後評価（b_feedback除去）。

### 2. Signal identifiability（対象に識別できる強さのsignalがあるか）

生のcryptoリターンは低S/N（G-Researchの教訓）。以下で識別可能性を確保する:

- **クロスセクション化**: 絶対リターンでなく相対順序のみ評価。市場全体の方向は採点対象から消える。
- **ユニバース幅 N=100**: 日次rank ICの標本ノイズはおよそ 1/√(N-1) ≈ 0.10。
- **日数 90日**: 平均ICの標準誤差はおよそ 0.10/√90 ≈ 0.011。IC 0.02〜0.03 の実力が統計的に見える設計。
- ユニバース選定（ラウンド開始時に固定）: 上場60日以上のHL perpから、直近30日の日次出来高中央値の上位100銘柄。選定クエリと結果リストは開始前に公開・封緘。

### 3. 共通成分の除去（target設計）

- **target**: 各銘柄の**horizon h∈{1,2,3,4}日先リターン**を直近30日の日次リターン標準偏差で割った**ボラ調整後リターン**のクロスセクション順位。1日の採点対象は 100銘柄 × 4horizon = 400個のtarget。
  - ボラ調整の理由: 生リターンの順位は高ボラ銘柄が両端を系統的に占め、順位が実質ボラ順になる。調整で「どの銘柄が相対的に強いか」だけが残る。
  - multi-horizon混在の理由: 単一horizonにしか効かない偶然の優位を、400個のtarget内で希釈する（MITSUI型）。
  - リターン定義: 00:00 UTCの基準価格から h 日後00:00 UTCの基準価格。基準価格はHL公式の日次snapshot（詳細は§6）。
- 追加のファクター中立化（BTCベータ、サイズ等）は第1回では行わない。日次IC分解を公開するので、事後分析で必要性を判断し第2回以降に導入する。

### 4. 指標と集計単位

- **提出**: (銘柄, horizon) の400ペアそれぞれへの score ∈ [0,1]（順序のみ意味を持つ）。`tradecore-signal-v1` スキーマはsymbol単位のため、キーを symbol×horizon に拡張する改修が必要（`testnet.mjs`への影響としてTCRED除去と併せて記録）。
- **日次IC**: その日の400ペアの提出scoreと実現targetのSpearman順位相関を1本にまとめて計算。1日=1観測。
- **最終スコア**: **IC Sharpe = mean(IC_t) / std(IC_t)**（約90観測）。mean ICも併記。
- **参考表示（採点外）**: 提出scoreの上位・下位20%を等ウェイトL/Sにした日次spreadリターン系列を公開する。ICという抽象量を、実際のL/S運用に近い数字へ翻訳して見せるための表示であり、順位には使わない。
- 参加資格: 提出日数がラウンド日数の80%以上。未提出日はその参加者のIC観測から除外（0埋めしない。0埋めはstdを歪める）。
- 注意: horizon 2〜4日は評価窓が日をまたいで重なるため、日次IC系列に自己相関が入る。IC Sharpeの解釈と§7のbootstrapはこれを前提にする（ブロック長はhorizon最大値以上、5日以上とする）。

### 5. 支配期間・支配銘柄の管理

- 日次ICの全系列を全参加者分公開。特定日・特定銘柄がスコアを支配していないかを誰でも検査できる。
- HL全体の障害日（事前定義: 公式ステータスで4時間以上の停止）は全員一律で採点から除外。
- ラウンド途中の上場廃止銘柄は、廃止日以降ユニバースから除外（事前ルール化。生存者バイアスはユニバース固定時点で開示）。
- multi-horizon混在（1〜4日）により、単一horizonにだけ効く偶然の優位は400target内で希釈される（第1回から採用）。

### 6. リーク管理（評価プロトコル）

- **封緘提出**: 毎日00:00 UTCの締切までに、署名付き予測（scoreの配列のハッシュ＋DID署名）を台帳に積む。対象期間の値動きは提出時点で未実現＝全評価がfuture data。
- **targetの再現可能性**: 基準価格はHL公開データ（我々のノードアーカイブも公開系列として提供）から誰でも再計算できる。target計算コードは開始前に公開・ハッシュ固定。
- **走行中の成績公開は行う**: 実現済み日のICは全公開。future data評価では過去の実現日への適応は正当なonline学習であり（Optiver Closeの教訓）、b_feedbackの再利用holdout問題は起きない。
- 同点処理・欠損処理・丸め・タイムゾーンはtarget計算コードが唯一の正であり、散文の仕様と食い違う場合はコードが勝つ（事前宣言）。

### 7. 順位の不確実性（標準装備）

- 最終順位表には必ず以下を併記する:
  - 各参加者のIC Sharpeの**block bootstrap信頼区間**（日次ICをブロック再標本化）
  - 上位陣の**ペア比較行列 P(AがBより上)** — 0.55の比較を順位の見た目で断定させない
- この表示はラウンドの一部であり、省略した順位発表は無効とする。

### メタモデルとvault運用（ユーザー決定: vaultで運用し、寄与度で収益分配）

ラウンドは測定だけの場ではなく、**メタモデルをHL vaultで実運用し、実現した収益を寄与度で参加者に分配する**。

- **メタモデル**: 全有効提出の等ウェイトrank合成（第1回。評判加重は将来検討）。日次ICを公開。
- **執行**: メタモデルのscoreから、事前登録したリスク枠（グロス上限・1銘柄上限・ネットゼロ近傍・日次リバランス）でL/Sポートフォリオを構成し、運営がvaultで執行する。リスク枠は開始前に封緘・公開し、ラウンド中は変更しない（変更が必要な事態は運用停止として扱い、台帳に記録）。
- **公開検証**: vaultの約定・成績はHL公開データで第三者検証できる（追記9）。日次の建玉・実現損益を台帳に積む。

### 寄与度と収益分配（数値は人間承認待ち）

- **原資**: ラウンド期間のvault実現ネット収益のX%（Xは開始前に固定・公開。人間承認事項）。HL vaultのleader収益分配の仕組みとの整合は実装時に確定。
- **寄与度**: 第1回の主指標は**MMC型**——参加者のsignalをメタモデルに直交化した残差と実現targetの日次相関の平均。メタと同じものを出しても寄与ゼロ、メタに無い独自情報だけが寄与になる（独自性への支払い）。診断用にleave-one-out ΔIC（その参加者を抜いたメタICとの差）も併載する。
- **分配**: 分配額 ∝ max(0, 寄与度)。寄与度にもbootstrap信頼区間を必ず併記（§7と同じ原則）。
- **負の寄与とvault損失**: vaultがネット損失の期は分配なし（参加者に請求はしない）。負の寄与は台帳に記録され、評判とエアドロップ重みに反映される。「損しても失うものがない」非対称は、まず負寄与の履歴化で抑え、荒れる場合はFLOP建てstake（追記7）を第2段階として導入する。
- **FLOPエアドロップ重み**: 参加・完走・正の寄与が加点対象（さかのぼり型・式非公開の原則は維持）。
- IC Sharpe順位表（§4・§7）は測定として維持するが、**支払いは順位でなく寄与度に基づく**。順位はsignalの質の公開測定、分配は実現収益への貢献、と役割を分ける。

### 台帳との接続

- ラウンド生成・提出・target確定・採点・賞金支払いはすべて台帳イベント（`ROUND_OPENED` / 署名付き提出 / `TARGET_PUBLISHED` / `ROUND_SCORED` / `PAYOUT`）。
- `src/testnet.mjs` の signal/target スキーマ（`tradecore-signal-v1` / `tradecore-target-v1`、ユニバース3〜200銘柄）は本仕様と整合。TCRED（faucet/stake/会計）部分のみ改修が必要。
- 各イベントはTechnocoreの`mb-`部屋へ署名付き告知（ハッシュ＋正本URL）を流す（追記7）。

## 設計とQ̂分解の対応表

| 設計 | 抑える項 |
|---|---|
| クロスセクション順位のみ評価 | δ_regime（市場方向との相互作用）、market beta |
| ボラ調整後リターンのrank | ボラスケール支配、外れ値 |
| N=100 × 90日、日次IC mean/std | ε_sampling |
| 毎日00:00 UTC封緘提出、future dataのみ | b_feedback |
| target計算コードの事前公開・ハッシュ固定、公開データで再計算可能 | b_protocol |
| bootstrap信頼区間とP(A>B)の必須表示 | 順位の過剰解釈（残った不確実性の開示） |
